# Правила CI и матрицы платформ PGR_M

## 1. Зачем существует CI

GitHub Actions повторяет три шага на чистых виртуальных машинах:

1. **Configure**: CMake читает проект, проверяет архитектурные зависимости.
2. **Build**: CMake запускает компилятор выбранной платформы.
3. **Test**: CTest запускает зарегистрированные тесты и сообщает об ошибках.

CI не заменяет локальную разработку, но проверяет, что сборка не зависит от
настроек конкретного ПК. Основная конфигурация находится в
`.github/workflows/ci.yml`, а не в отдельном дублирующем build-скрипте.

## 2. Когда запускается workflow

- `push` в `main`;
- `pull_request` в `main`;
- ручной запуск через `workflow_dispatch`.

Изменение исключительно `site/**` исключено из автоматического запуска:
сайт сейчас не участвует в C++-сборке. Изменения `CMakeLists.txt`, `cmake/`,
`app/`, `modules/`, `tests/`, `docs/` и `.github/` НЕ исключаются.
Для защищённой `main` настройте required status checks в GitHub.

Права workflow ограничены `contents: read`. Тесты не требуют токенов,
паролей или секретов. Не публикуйте в логах ключи и локальные пути с секретами.

## 3. Первая матрица: ОС × конфигурация

В `platforms` переменные `matrix.os` и `matrix.configuration` образуют
декартово произведение **3 × 2 = 6 заданий**:

| Runner GitHub | Конфигурации | Компилятор по умолчанию |
|---|---|---|
| `ubuntu-24.04` | Debug, Release | Обычно GCC |
| `windows-2022` | Debug, Release | Обычно MSVC (Visual Studio) |
| `macos-15` | Debug, Release | Обычно Apple Clang |

Названия ОС закреплены на версиях runner, но фактические патч-версии
компиляторов/SDK могут изменяться при обновлениях образов GitHub.
Для абсолютной воспроизводимости инструменты нужно фиксировать отдельно.

Во всех шести заданиях включены `core`, `gui`, `nn` и тесты.
Флаг `fail-fast: false` позволяет получить ошибки разных ОС сразу.
Каждое задание запускается в отдельной виртуальной машине и не использует
артефакты от другого задания. `--config` необходим для Visual Studio,
а `CMAKE_BUILD_TYPE` — для Ninja/Make.

## 4. Вторая матрица: проверка независимости модулей

Отдельное задание `independent-modules` запускается на Ubuntu 24.04
в Debug с четырьмя наборами включённых целей:

| Профиль | core | gui | nn |
|---|---|---|---|
| `none` | OFF | OFF | OFF |
| `core-only` | ON | OFF | OFF |
| `gui-only` | OFF | ON | OFF |
| `nn-only` | OFF | OFF | ON |

Это ещё **4 задания**. Итого текущий CI запускает **10 заданий**.
Первая матрица проверяет совместную сборку, вторая — возможность
создать приложение без любых двух модулей. Межмодульные CMake-связи
дополнительно блокирует `cmake/CheckModuleIndependence.cmake`.

Ограничения: пока `core/gui/nn` пустые, проверяется лишь структура сборки,
а не функциональность этих модулей. Smoke-тест проверяет запуск `app` и
строку `Hello, World!`; он не доказывает корректность алгоритмов. При
появлении кода добавляйте настоящие модульные тесты и при необходимости
расширяйте матрицу до всех восьми сочетаний ON/OFF.

## 5. Как читать и изменять workflow

- `name` — название workflow и заданий в GitHub UI.
- `on` — события запуска.
- `permissions` — разрешения встроенного токена.
- `jobs` — независимые задания.
- `runs-on` — образ runner.
- `strategy.matrix` — массивы параметров, перемножаемые GitHub.
- `matrix.profile` — массив объектов с согласованными флагами модулей.
- `steps` — последовательность действий в рамках одного задания.
- `uses: actions/checkout@v4` — загрузка кода на runner.
- `run: cmake ...` — команды CMake/CTest.

Добавляя новую ОС, убедитесь, что на runner есть CMake >= 3.20 и C++17,
что внешние зависимости GUI/NN доступны на платформе и что smoke-тест
способен запускаться без графического дисплея. Если GUI требует дисплей,
выделите headless-тесты и настройте виртуальный дисплей отдельно. Не
пытайтесь маскировать такую проблему отключением всех тестов.

Добавляя новый компилятор (например, Clang на Ubuntu), используйте
**новое** дерево сборки и явные `CC`/`CXX` до первой конфигурации.
Не меняйте компилятор внутри существующего CMakeCache.txt.

## 6. Требования к pull request и правила поддержки

1. Изменения CMake сопровождаются правкой `docs/CMAKE.md`, если меняются
   структура, параметры, зависимости или путь к бинарному файлу.
2. Изменения CI сопровождаются обновлением этого документа и числа задач.
3. Каждая новая внешняя библиотека должна иметь установку либо надёжное
   обнаружение на всех трёх платформах. Если платформа временно не
   поддерживается, явно объясните причину в документации и CI.
4. Не удаляйте задания из матрицы для сокрытия ошибки сборки.
5. Не добавляйте секреты в CMakeCache.txt, журнал CTest или артефакты CI.
6. Перед объединением PR дождитесь успешных основных проверок; на самой
   платформе также проводите локальные проверки ввода/вывода и GUI.

## 7. Запуск проверок локально

Имитировать одно задание матрицы можно на Linux так:

```sh
cmake -S . -B build/ci -DCMAKE_BUILD_TYPE=Release \
  -DPGR_BUILD_CORE=ON -DPGR_BUILD_GUI=ON -DPGR_BUILD_NN=ON \
  -DPGR_BUILD_TESTS=ON
cmake --build build/ci --config Release --parallel 2
ctest --test-dir build/ci -C Release --output-on-failure --no-tests=error
```

Для изменения профиля используйте **новый** каталог `-B`, например
`build/local/gui-only`, и установите `core=OFF`, `gui=ON`, `nn=OFF`.

Если CI упал, смотрите сначала шаг **Конфигурация CMake** (ошибки в
зависимостях), затем **Скомпилировать приложение** (ошибки компиляции),
затем **Запустить CTest** (ошибки выполнения/тестов). Повторный запуск
без исправления причины редко даёт полезную информацию.
